# 实车启动排查手册

> 场景：哨兵连裁判系统 + 比赛开始 + 启动导航/串口/决策全栈。
> 用法：按顺序逐项检查，每项给出「正常表现」和「异常排查」。有异常把对应的
>       `ros2 topic echo` 输出 / 日志贴出来定位。
> 前提认知：决策只在**收到裁判数据 + 定位就绪**后才会发导航目标；任一缺失都会卡在 IDLE 或原地不动。

---

## 0. 一分钟快速判断"决策活没活"

```bash
# 决策节点的状态日志（每次状态切换会打印）
ros2 topic echo /goal_pose            # 决策发的导航目标；一直没输出 = 决策没发目标
ros2 node list | grep decision        # 决策节点在不在
```

- **一直无 /goal_pose 输出** → 决策停在 IDLE（裁判没数据/比赛没开始/定位没起），往下逐项查。
- **有输出但车不动** → 决策正常，问题在 Nav2/定位/串口，看第 3、4 节。

---

## 1. 串口 ↔ 电控（裁判数据入口）

决策的血量/弹药/比赛状态全部来自电控经串口上报。**串口不通 = 决策永远 IDLE**。

```bash
# 四个裁判话题都要有数据（串口驱动发布）
ros2 topic hz /referee/game_status      # 正常 ~几Hz
ros2 topic echo /referee/robot_status --once   # 看 current_hp / projectile_allowance_17mm
ros2 topic echo /referee/game_status --once    # 看 game_progress
ros2 topic echo /referee/all_robot_hp --once   # 看 ally_outpost_hp（前哨站血量）
```

| 检查 | 正常 | 异常排查 |
|------|------|----------|
| 四个 referee 话题有数据 | hz>0，字段非全 0 | 串口驱动没连上电控 / USB 口错 / 波特率；看串口驱动日志有无 "reopen port" |
| `game_progress` | 比赛中=4 | 若一直≠4，决策不会离开 IDLE（这是对的） |
| `current_hp` | 满血 400 附近 | 若=0 但哨兵活着，检查电控上报 |
| `ally_outpost_hp` | 前哨站真实血量 | 决定走前压还是防守路线 |

> ⚠️ **已知**：电控 `stage_remain_time` 可能写死 400（调试值）。决策 `game_running()` 主要靠 `game_progress` 判断，400 在合法范围（≤420）不影响启动。但若你要用真实剩余时间，让电控改回真值。

## 2. 定位（决策位置判断 + goal 能否被 Nav2 接收的根基）

决策订阅 `odometry`，内部经 tf2 把位置转到 `map` 系。Nav2 也在 map 系规划。
**map→odom 不存在 → 决策位置判断失效 + Nav2 拒绝 goal（车不动）**。

```bash
# ① odom 里程计（point_lio 发布）—— 决策订阅这个
ros2 topic hz /odometry                 # 决策订阅这个(由 odom_bridge 发布, 名字匹配)
ros2 topic hz /aft_mapped_to_init       # point_lio 的输出(odom_bridge 的输入)
ros2 node list | grep odom_bridge       # 桥接节点在不在
# ② map->odom 变换（重定位 small_gicp 发布）—— 最关键
ros2 run tf2_ros tf2_echo map odom      # 必须持续输出、数值稳定
# ③ 机器人在 map 的位置
ros2 run tf2_ros tf2_echo map gimbal_yaw
```

| 检查 | 正常 | 异常排查 |
|------|------|----------|
| `/odometry` 有数据 | hz>0 | 见下方 odom_bridge 链路排查 |
| `tf2_echo map odom` | 持续输出、不乱跳 | 重定位没起/没初始化 → **goal 会被 Nav2 拒，车不动**（不是决策的错） |
| map→gimbal_yaw 位置 | 和实际位置吻合 | 重定位漂移 → 标定坐标全偏，哨兵跑错地方 |

> ⚠️ **里程计链路(实车最该查的)**：决策订阅的 `odometry` 由 **odom_bridge** 节点发布，
> 链路是 `point_lio(aft_mapped_to_init) → odom_bridge → odometry`。话题名是**匹配的**，
> 不用 remap。真正的坑是 **odom_bridge 单点**：它用 message_filters 严格同步
> `aft_mapped_to_init` + `cloud_registered` 两路，任一缺失/时间戳对不齐就**不发 odometry**。
> 排查：`/aft_mapped_to_init` 有数据但 `/odometry` 没有 → odom_bridge 没起或同步失败。

## 3. Nav2 导航（决策发 goal → 车规划执行）

```bash
# 决策发的目标
ros2 topic echo /goal_pose
# Nav2 action 是否在
ros2 action list | grep navigate_to_pose
# Nav2 有没有报 TF/规划错误
# （看 Nav2 终端日志：Could not transform / failed to get plan）
```

| 检查 | 正常 | 异常排查 |
|------|------|----------|
| navigate_to_pose action 存在 | 在列表里 | Nav2 没起；决策会降级发 /goal_pose topic |
| 决策发的 goal frame | `map` | — |
| Nav2 接收 goal | 开始规划、车动 | 报 "Could not transform map→..." = 定位没起（回第2节）；报 "failed to get plan" = 目标点不可达/在障碍里/坐标标错 |
| 车走向的点 | 和决策日志里的目标一致 | 坐标标错（见第2节漂移） |

> **决策的降级**：Nav2 action 不可用时，决策自动改发 `/goal_pose` topic + 用 odom 距离判到达。所以即使 Nav2 没起，决策也不会崩，但需要有节点消费 /goal_pose。

## 4. 决策行为验证（逻辑对不对）

裁判数据 + 定位都就绪后，验证决策的状态切换是否符合预期。看决策节点终端的状态日志。

| 场景 | 预期状态 | 预期目标 |
|------|----------|----------|
| 比赛开始、满血满弹、前哨站存活 | OPENING_STRIKE(开局一次) → 之后 PATROL 走 patrol_aggressive(前压) | opening_strike(7.348,0.242) → 前压点 |
| 比赛开始、满血满弹、前哨站被摧毁 | PATROL 走 patrol(默认三点) | 巡逻点1/2/3 |
| hp<150 或 弹药≤50 | RESUPPLY | supply(0.327,-0.216) |
| 裁判断连>3s / 比赛结束 | IDLE | 取消导航，原地 |

> ⚠️ **注意前压 vs 巡逻**：前哨站**存活**时走 `patrol_aggressive`（当前是占位点 8.0,0.0），**被摧毁**才走你标的三个巡逻点。测巡逻点要么让前哨站血量=0，要么先把 patrol_aggressive 也标定好。

> ⚠️ **注意开局打点**：配了 opening_strike，比赛一开始哨兵会先去 (7.348,0.242) 停 90s（opening_strike_duration_s）才转巡逻。想直接测巡逻，临时把该时长调小或删掉 opening_strike 项。

## 5. 过起伏路段（当前默认关闭）

**现状：`bump_segments` 全注释 = 功能关闭。** 你给的坐标里没有起伏段，所以现在即使全实车，过起伏也不会触发。要测需先：

1. 标定起伏段 entry/exit（map 系，`tf2_echo map gimbal_yaw`），entry.y≈exit.y
2. 填进 rmuc_red.yaml 的 bump_segments，去掉注释
3. **先平地假坎验证**（见实车测试指南 4.5），dash_speed 从 0.8 起
4. `ros2 topic echo cmd_vel_chassis` 确认冲刺时只有 linear.x

## 6. 一页速查（按顺序，卡在哪查哪）

```
车不动 / 决策没发 goal
  │
  ├─ 1. referee 四话题有数据吗？  ros2 topic hz /referee/game_status
  │      无 → 串口/电控问题
  │
  ├─ 2. game_progress == 4 吗？   ros2 topic echo /referee/game_status --once
  │      否 → 比赛没开始，决策 IDLE（正常）
  │
  ├─ 3. /odometry 有数据吗？      ros2 topic hz /odometry
  │      无 → point_lio/雷达，或话题名不匹配
  │
  ├─ 4. map->odom 稳定吗？        ros2 run tf2_ros tf2_echo map odom
  │      无/乱跳 → 重定位没起 → Nav2 拒 goal（关键！）
  │
  ├─ 5. 决策发 goal 了吗？        ros2 topic echo /goal_pose
  │      有 → 决策正常，问题在 Nav2/定位
  │      无 → 回 1-4
  │
  └─ 6. Nav2 报错？               看 Nav2 日志
         Could not transform → 定位（回 4）
         failed to get plan   → 目标不可达/坐标标错
```

## 关于"能不能提前检查出问题"

**代码层面的问题**（话题名、逻辑、坐标加载）本文档已尽量提前列出。
**运行时问题**（串口没插、雷达没出点云、定位漂移、目标不可达）无法事前预知，只能按上表现场定位——把对应命令的输出贴出来即可分析。

**最高频的三个坑**（按经验排序）：
1. odom_bridge 没起/时间同步失败 → /odometry 不发 → 决策收不到位置(话题名本身是匹配的)
2. 重定位没就绪 → map→odom 缺失 → Nav2 拒 goal
3. 前哨站存活走了 patrol_aggressive 占位点，不是你标的巡逻点
