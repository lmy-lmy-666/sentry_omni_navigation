## 二、架构审查

### 2.1 分层与依赖（优秀）

```
types.hpp        ← 纯数据，零依赖
profile.hpp      → types
context.hpp      → types + rm_interfaces（世界模型，无 FSM/ROS 逻辑）
arrival_tracker.hpp → types（无 ROS 的到达判定）
fsm.hpp          → context + profile（纯逻辑，std::function 回调解耦）
decision_node.hpp → 全部 + ROS（唯一 ROS 层）
```

- **单向依赖**，无循环。`DecisionFsm` 和 `Context` 零 ROS 依赖，这是 55 个单测能脱离 ROS 运行的根本原因。
- **回调解耦**：FSM 通过 `GoalPublisher / NavCanceller / BumpVelPublisher` 三个 `std::function` 与节点通信，不直接依赖 ROS 类型。教科书式设计。

### 2.2 状态机设计（优秀）

5 态优先级链 + 每 tick 重评估，逻辑集中在 `select_state()`。
- 优先级 `IDLE > BUMP_TRAVERSE > RESUPPLY > OPENING_STRIKE > PATROL` 清晰且有注释。
- 防振荡三重机制：HP/弹药迟滞、`min_ticks_in_state`、路线切换重置追踪。
- **抢占屏蔽纵深防御**：BUMP_TRAVERSE 冲刺中的保护同时存在于 `select_state`（强制返回）和 `can_leave_current_state`（拒绝离开）两层，任一失效另一层兜底——这是本次审查中特别值得肯定的健壮设计。

## 三、发现的问题（按严重度排序）

审查采用置信度评分，只列高置信度问题。以下均为**真实存在**、经代码核实的项。

### 🟡 中等 — M1：DONE 后可能与业务状态反复横跳（理论风险）

**位置**：`fsm.cpp` select_state 第 73-136 行
**现象**：过起伏 DONE 后，select_state 重算业务状态并**再次调用 `find_bump_to_cross`**。正常情况下哨兵已到对侧、目标在同侧，不会重触发。但存在一个边界：若 DONE 那一刻业务状态恰好切换（如 PATROL→RESUPPLY），而新目标（补给点）又在刚过来的那一侧，会**立即再次触发 BUMP_TRAVERSE 反向冲回**。
**影响**：极端情况下可能在起伏段两侧反复横跳。实战概率低（需要"刚过完坡瞬间血量掉到补给线且补给点在对岸"），但逻辑上未被完全排除。
**建议**：DONE 后加一个短冷却（如 N tick 内不重触发同一段），或 DONE 时记录"刚过完的段"本 tick 不再评估。当前未做，属可接受的已知边界。

### 🟡 中等 — M2：坐标标定文档原用错坐标系（已修正）

**类型**：文档缺陷（非代码缺陷），但实操影响大。
**位置**：`docs/坐标标定说明.md` 原第 3 步、两份 profile YAML 的标定注释。
**现象**：原标定流程主推 `ros2 topic echo /odometry` 读坐标，但 `/odometry` 是 **odom 系**；而决策发给 Nav2 的 goal 是 **map 系**，决策内部也把 odom 位置经 tf2 转到 map 系再用。两者不是同一坐标系。
**影响**：重定位（small_gicp_relocalization 建立 map→odom）一旦有偏移，按 odom 系标出的坐标填进 YAML 后，哨兵会**系统性跑偏**——且很隐蔽，因为坐标"看起来对"。起伏段坐标标错还可能导致过起伏冲错方向。
**根因链**：`map ─(重定位)→ odom ─(point_lio)→ gimbal_yaw`。标定必须拿 map 系（决策/Nav2 实际用的系），不能拿 odom 系原始值。
**修正**（已完成）：标定改为 `ros2 run tf2_ros tf2_echo map gimbal_yaw` 读 map 系坐标；标定前先 `tf2_echo map odom` 确认重定位就绪；文档与两份 YAML 注释同步更正并明确警告"不要读 /odometry"。

### 🟢 轻微（已修复）— L1：`bump_stop_ticks` 曾是死配置项

**位置**：`types.hpp:113` 声明、`profile.cpp:109` 解析、YAML 中配置
**现象**：`bump_stop_ticks`（"DONE 时发几帧零速再交还"）被声明、解析、写进 YAML，**但从未被读取使用**。`bump_stop_frames_` 在 DONE 里递增，却没有与 `bump_stop_ticks` 比较。
**实际行为**：DONE 状态每 tick 发零速，直到 select_state 因业务状态就绪而离开——不是"发够 N 帧就走"。功能上无害（照样会交还），但**配置项名不副实**，注释与实现不符。
**修复**（已完成）：让 `bump_stop_ticks` 真正生效——DONE 后在 select_state 里判断 `bump_stop_frames_ < bump_stop_ticks` 时保持 BUMP_TRAVERSE（settling），发够帧才交还。新增 `DoneSettlesForConfiguredStopTicks` 测试验证。

### 🟢 轻微（已修复）— L2：`bump_return_state_` 曾是死变量

**位置**：原 `fsm.hpp` 声明、`fsm.cpp` 赋值
**现象**：进入 BUMP 时记录了 `bump_return_state_`，但 DONE 后实际靠 select_state 重算业务状态，从不读它。
**修复**（已完成）：删除该成员及其赋值，注释同步修正为"靠 select_state 重算"。

### 🟢 轻微 — L3：DASHING 恒速无上限保护（未修）

**位置**：`fsm.cpp` bump_dash_vx()
**现象**：`bump_dash_speed` 直接来自 YAML，无上限钳制。若误配成很大的值（如 5.0 m/s），会直接发给底盘。
**影响**：配置错误会导致危险高速冲刺。目前靠"实车先低速"的流程约束，代码层无护栏。
**建议**：加一个 `bump_dash_speed` 的合理上限校验（如启动时 assert ≤ 2.0），防呆。

## 五、安全审查

### 5.1 物理安全（重点）

**过起伏开环直驱底盘**是本模块最高物理风险点：DASHING 阶段决策绕过 Nav2 避障，直接发速度驱动底盘。已有的缓解措施：

| 缓解 | 状态 |
|------|------|
| 冲刺超时（bump_timeout_s）→ 反向退回 | ✅ 已实现 |
| IDLE（比赛结束/断连）可随时打断 → 停车 | ✅ 已实现 |
| 位置丢失盲走而非乱冲 | ✅ 已实现 |
| dash_speed 上限校验 | ❌ 未做（见 L3） |
| 实车先平地假坎、低速起步 | ⚠️ 靠流程约束，文档已强调 |

### 5.2 数据安全（优秀）

- 所有裁判数据 `std::optional` 保护，null 返回安全默认值
- 串口不报 max_hp → 用配置值；RFID 错映射 → 位置到达兜底；裁判断流 → IDLE
- 无秘密/凭证处理，无网络暴露面（纯本地 ROS 节点）

### 5.3 边界安全

- `find_bump_to_cross` 有 `bump_disabled_` 数组访问，索引来自自身循环，无越界风险
- YAML 解析有 NaN/Inf 校验、y 对齐校验、空列表处理，加载健壮
- 除 M1 的理论横跳外，未发现空指针/越界/资源泄露/竞态

## 六、电控对接审查

已核实完整链路（决策 → 串口驱动 → 电控），话题名与字段映射一致：

```
决策 publish_bump_vel → /cmd_vel_chassis (Twist)
  → rm_serial_driver 订阅, lx=linear.x/ly=linear.y/az=angular.z
  → control 帧(0xA0) + CRC16 → USB CDC → 电控舵轮
```

**对接结论**：链路通、映射对。职责边界清晰——导航侧只发速度，mode（小陀螺/estop）归电控内部管。

**依赖电控侧（非本模块，已记入 ANALYSIS 11.1）**：
1. 电控"受击小陀螺"若实装，必须与移动/过起伏互斥（冲刺中旋转=舵轮翻车）
2. `stage_remain_time` 电控写死 400、`ros_state` 写死 2 —— 信号未接真，但当前决策不用，无害；用到时再改
