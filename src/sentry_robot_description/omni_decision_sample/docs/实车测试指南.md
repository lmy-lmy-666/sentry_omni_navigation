# Sentry Decision 实车导航测试指南

没有裁判系统的前提下，用 mock 节点模拟裁判数据，在实车上验证巡逻、残血回家、补给、阵亡复活回归的导航逻辑。推荐用交互式工具 `mock_referee_tui.py`（见下方「推荐工具」）。

---

## 前提条件

- 实车上已部署 `omni_decision_sample` 包
- Nav2 导航栈正常运行
- 里程计正常发布（注意话题名！决策默认订阅 `odometry`，实车可能是 `/Odometry` 等）
- YAML 配置文件中的巡逻点和补给点坐标已对过实际场地

> 说明：决策的"满血"判定用 profile 里配置的 `max_hp`(默认 400)，**不依赖** `robot_status` 消息里的 `maximum_hp` 字段（串口不上报，恒为 0）。下面命令里带的 `maximum_hp: 400` 只是填个合法值，决策实际不看它。到达补给区判定以**位置到达为主**，RFID 为辅。

---

## 推荐工具（四个脚本）

| 脚本 | 形式 | 什么时候用 |
|------|------|-----------|
| `preflight_check.py` | 命令行自检：确认裁判/odom/Nav2 数据流通 | 上场前、每次开测前 |
| `mock_referee_gui.py` | **图形界面按钮**（点按钮/拖滑块），有显示器时首选 | 实车调试 |
| `mock_referee_tui.py` | 交互式键盘控制，无显示器/纯 SSH 时用 | 实车调试 |
| `mock_referee.py` | 固定参数发假数据（非交互） | 脚本化/自动化测试 |

> `mock_referee_gui.py` 需要图形环境（`DISPLAY`）。纯 SSH 无转发时退回键盘版 `mock_referee_tui.py`，两者功能一致。

### 开测前先自检

```bash
# 先确认 odom 真实话题名
ros2 topic list | grep -i odom

# 用真实话题名跑自检（假设是 /Odometry）
ros2 run omni_decision_sample preflight_check.py --ros-args -p odom_topic:=/Odometry
```

全部 `[ OK ]` 再往下测。任何 `[FAIL]` 都说明对应链路没通，先修。

### 可视化测试（有显示器时首选）

启动后弹出窗口，点按钮/拖滑块实时改状态，最直观。

```bash
# 终端1：可视化 mock 裁判（弹出图形窗口）
ros2 run omni_decision_sample mock_referee_gui.py

# 终端2：决策节点（默认红方；蓝方加 profile:=rmuc_blue.yaml）
ros2 launch omni_decision_sample omni_decision_sample_launch.py

# 终端3(可选)：看导航目标
ros2 topic echo /goal_pose
```

窗口分四块：
- **当前状态**：实时显示 hp / ammo / game / 前哨站
- **一键场景**：6 个按钮（满血/残血/弹药低/阵亡/复活/恢复满）
- **开关**：切前哨站存活/被击毁、切比赛进行中/未开始
- **微调滑块**：血量、弹药拖动实时生效（测边界值好用）

推荐点按顺序：① 满血 → 切前哨站 → ② 残血 → ④ 阵亡 → ⑤ 复活 → ⑥ 恢复满，对照终端2决策日志 `state -> XXX | reason` 确认。

### 交互式测试（键盘版，无显示器时用）

以 10Hz 持续发数据保持 referee 新鲜，按键实时改状态。

```bash
# 终端1：键盘交互 mock 裁判
ros2 run omni_decision_sample mock_referee_tui.py

# 终端2：决策节点（默认红方；蓝方加 profile:=rmuc_blue.yaml）
ros2 launch omni_decision_sample omni_decision_sample_launch.py

# 终端3(可选)：看导航目标
ros2 topic echo /goal_pose
```

焦点放终端1，按键即可：

| 键 | 效果 | 决策应有反应 |
|----|------|-------------|
| `1` | 满血满弹 | → PATROL |
| `2` | 残血 (hp=100) | → RESUPPLY (hp low) |
| `3` | 弹药低 (ammo=40) | → RESUPPLY (ammo low) |
| `4` | 阵亡 (hp=0) | 保持 RESUPPLY，持续发目标不卡死 |
| `5` | 复活 (hp=40) | 仍 RESUPPLY，继续回补给点 |
| `6` | 恢复满 | → PATROL |
| `o` | 切前哨站 存活/被击毁 | 巡逻路线 前压↔半场防守 |
| `+`/`-` | 血量 ±50 | 测血量边界 |
| `]`/`[` | 弹药 ±50 | 测弹药边界 |
| `g` | 切比赛 进行中/未开始 | 未开始→决策进 IDLE |
| `p` | 打印当前状态 | — |
| `q` | 退出 | — |

推荐测试顺序：`1`(巡逻) → `o`(切路线) → `2`(残血回家) → `4`(阵亡不卡死) → `5`(复活回归) → `6`(恢复出击)。每次按键对照终端2决策日志的 `state -> XXX | reason` 确认。

> 下面的「章节一~七」是用非交互的 `mock_referee.py` + `topic pub` 的详细手动流程，作为交互工具的补充参考（比如要精确复现某个边界值时）。

## 零、测试开局打前哨站（OPENING_STRIKE）

前提：profile 里配了 `opening_strike` 坐标（默认已配占位符）。若删掉该项则此功能关闭，哨兵开局直接巡逻。

### 步骤

```bash
# 满血满弹、比赛开局
ros2 run omni_decision_sample mock_referee.py \
  --ros-args -p hp:=400 -p ammo:=300 -p max_hp:=400 -p remain:=420
# 决策节点另开一终端启动
```

### 预期行为

- 开局日志 `state -> OPENING_STRIKE | reason: opening strike start`
- 导航目标是 `opening_strike` 坐标，哨兵去打点位并停在那里
- 停留 `opening_strike_duration_s`（默认 90s）后 → `OPENING_STRIKE -> PATROL`，转正常巡逻
- **只做一次**：之后即使再满血也不会回打点位

### 打点期间掉血 → 回补给（验证优先级）

```bash
# 打点途中把血打低
ros2 topic pub /referee/robot_status rm_interfaces/msg/RobotStatus \
  "{current_hp: 100, maximum_hp: 400, projectile_allowance_17mm: 300}" --once
```

预期：`OPENING_STRIKE -> RESUPPLY`（血弹不足优先回补给）；补满后进 PATROL，**不再回打点**（开局打点已消费）。

> 提示：想快速看到"结束打点"的切换，可临时把 profile 里 `opening_strike_duration_s` 调小（如 5.0）测试，测完改回 90.0。

## 一、测试巡逻

### 步骤

```bash
# 终端 1：启动 mock 裁判（满血满弹，比赛进行中；ammo 要 >50 才不会触发补给）
# 注意: 若 profile 配了 opening_strike, 哨兵会先打点 90s 才巡逻; 想直接测巡逻可临时删掉该项或把时长调到 0
ros2 run omni_decision_sample mock_referee.py \
  --ros-args -p hp:=400 -p ammo:=300 -p max_hp:=400 -p remain:=300

# 终端 2：启动决策节点（按你的 launch 文件启动）
ros2 launch omni_decision_sample omni_decision_sample_launch.py
```

### 预期行为

- 决策节点日志显示 `state -> PATROL`
- 我方前哨站血量 >0 时走 `patrol_aggressive`（前压路线，如果有配置）
- 前哨站血量 =0 时走默认 `patrol`（我方半场防守）
- 到达每个点停留 `dwell_s` 秒后去下一个
- 单点卡住超过 10s 自动跳下一个点

### 观察方式

```bash
# 看决策节点状态切换
ros2 topic echo /omni_decision_sample/state  # 如果有的话，或者看终端日志

# 看导航目标
ros2 topic echo /goal_pose
```

## 二、测试残血回家（RESUPPLY - 血量触发）

### 步骤

```bash
# 先正常跑起来（同上一步骤 1、2）

# 终端 3：敲完装甲板后，手动把血量打到 100（< 150 补给阈值）
ros2 topic pub /referee/robot_status rm_interfaces/msg/RobotStatus \
  "{current_hp: 100, maximum_hp: 400, projectile_allowance_17mm: 300}" --once
```

### 预期行为

- 决策节点日志显示 `state -> RESUPPLY | reason: hp low`
- 机器人停止巡逻，导航目标切换为补给点坐标
- 机器人向补给点移动
- RFID 检测到踩上补给区 → 原地等待被动回血
- 导航卡住/超时（30s）会轮换候选点再回主点，**永不放弃**

### 验证回满后退出

```bash
# 模拟血量恢复但没满
ros2 topic pub /referee/robot_status rm_interfaces/msg/RobotStatus \
  "{current_hp: 399, maximum_hp: 400, projectile_allowance_17mm: 300}" --once
```

预期：**保持 RESUPPLY**（未回满 400，继续等）。

```bash
# 模拟血量回满
ros2 topic pub /referee/robot_status rm_interfaces/msg/RobotStatus \
  "{current_hp: 400, maximum_hp: 400, projectile_allowance_17mm: 300}" --once
```

预期：`RESUPPLY → PATROL`，恢复正常巡逻（血满且弹药≥100）。

## 四、测试阵亡复活回归（关键）

验证哨兵阵亡后不会卡在原地、复活后能自动回补给区。

### 步骤

```bash
# 模拟阵亡：血量 0
ros2 topic pub /referee/robot_status rm_interfaces/msg/RobotStatus \
  "{current_hp: 0, maximum_hp: 400, projectile_allowance_17mm: 300}" --once

# 等待较长时间（模拟读条复活期，比如 30-60s）……
# 期间决策应保持 RESUPPLY 并持续朝补给点发目标

# 模拟复活：血量恢复到 10%（40）
ros2 topic pub /referee/robot_status rm_interfaces/msg/RobotStatus \
  "{current_hp: 40, maximum_hp: 400, projectile_allowance_17mm: 300}" --once
```

### 预期行为

- 阵亡（hp=0）时保持 `RESUPPLY`，持续朝补给点发导航目标（不会因超时停下）
- 复活（hp=40 < 150）后仍在 `RESUPPLY`，继续导航回补给区
- 回满 400 后才 `RESUPPLY → PATROL`

## 四点五、测试过起伏路段（BUMP_TRAVERSE）⚠️ 底盘直驱，务必先低速

> ⚠️ **安全第一**：穿越阶段决策节点**绕过 Nav2 直发 `cmd_vel_chassis` 驱动底盘**。务必：
> ① 先在**平地假坎**跑通全流程；② `bump_dash_speed` 先设 0.8 低速；③ 手边留急停（比赛结束/断裁判即零速）；④ 舵轮确认能转正对齐再上真实起伏段。

### 前置：先配一段"假坎"（平地虚拟起伏段）

在平地上选一段直线（比如 x 从 1 到 4，y 固定），填进 profile 的 `bump_segments`，并把巡逻点配在段的**对侧**，这样哨兵一巡逻就会触发过起伏段：

```yaml
patrol:
  - {x: 6.0, y: 0.0, dwell_s: 10.0}   # 段的对侧, 逼哨兵穿过
bump_segments:
  - entry: {x: 1.0, y: 0.0}
    exit:  {x: 4.0, y: 0.0}
    yaw: 0.0
```

### 步骤

```bash
# 满血满弹、比赛进行中，让哨兵去巡逻(对侧目标) → 途中触发过起伏段
# 起始位置放在段的近侧(x<1)
```

### 预期行为（看状态日志 + echo cmd_vel_chassis）

1. `PATROL/…` → `BUMP_TRAVERSE`，reason 打印 "bump segment between us and goal"
2. GOTO_ENTRY：先发 Nav2 goal 到入口 (x=1)，车开过去对正
3. ALIGN：到入口后 cancel Nav2，静默 ~0.5s（`cmd_vel_chassis` 输出 0）
4. DASHING：`cmd_vel_chassis` 输出**恒定** `linear.x=0.8`（y=0, angular.z=0），全程不减速
5. 越过出口 x=4 → 立即零速，`BUMP_TRAVERSE → PATROL`

```bash
# 另开终端盯底盘速度, 确认穿越期只有 linear.x, 且恒速
ros2 topic echo cmd_vel_chassis
```

### 关键验证点

```bash
# ① 恒速不减速: 接近出口时 linear.x 仍是 0.8, 不下降
# ② 抢占屏蔽: 穿越途中把血打到 50(<150), 状态必须仍是 BUMP_TRAVERSE, 不切 RESUPPLY
# ③ IDLE 急停: 穿越途中把比赛设为 GAME_OVER, 必须立即 IDLE + 零速
# ④ 盲走: 穿越途中遮挡雷达/断 TF, 车不应停(保持上一帧速度冲完)
# ⑤ 超时反向: 挡住车让它过不去, 20s 后应反向低速退回入口
```

### 上真实起伏段前的递进

1. 平地假坎全流程通过（上面 ①~⑤ 全过）
2. 真实起伏段 `bump_dash_speed` 从 0.8 起，逐步加到能稳定翻过波浪的值
3. 红蓝双方起伏段坐标各自实测标定，不共用

## 五、边界值测试

| 触发条件 | 命令中的值 | 预期状态 | 原因 |
|----------|-------------|----------|------|
| 补给门槛不进 RESUPPLY | hp=150 | PATROL | hp < 150 才触发，=150 不触发 |
| 刚好进 RESUPPLY | hp=149 | RESUPPLY | < 150 触发 |
| 弹药门槛不进 | ammo=51 | PATROL | ammo ≤ 50 才触发 |
| 刚好进 RESUPPLY | ammo=50 | RESUPPLY | ≤ 50 触发 |
| 回血未满不退出 | hp=399 | RESUPPLY 保持 | 退出需 hp 满 400 |
| 弹药未够不退出 | ammo=99 | RESUPPLY 保持 | 退出需 ammo ≥ 100 |
| 阵亡不卡死 | hp=0 | RESUPPLY 持续导航 | 永不放弃 |

## 七、故障排查

| 现象 | 可能原因 | 检查 |
|------|----------|------|
| 决策一直在 IDLE | mock 没跑或话题名不对 | `ros2 topic echo /referee/game_status` |
| 状态不切换 | 发的话题类型不对 | 检查 msg 类型 `ros2 interface show rm_interfaces/msg/RobotStatus` |
| 导航目标发了但机器人不动 | Nav2 没跑 | `ros2 action list \| grep navigate` |
| 巡逻路线不对 | YAML 配置坐标问题 | 检查 `patrol` 字段里的 x,y 值 |
| RFID 补给检测不触发 | RFID 话题字段名可能不对 | `ros2 interface show rm_interfaces/msg/RfidStatus` |
